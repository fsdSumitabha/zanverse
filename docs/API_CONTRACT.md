# API contract for the mobile app

## Auth flow
LOGIN. The login screen POSTs { email, password } to /api/auth/login. The server looks the user up outside the region scope, checks isActive (403 "Account is deactivated") and bcrypt-compares the password (401 "Invalid credentials"), then signs a jose HS256 JWT with payload { userId, role, regions } and setIssuedAt + setExpirationTime("7d"). Before setting the new cookie it DELETES the active_region cookie so a region pin left by a previous user on the same browser cannot carry over. It then sets auth_token with exactly: httpOnly: true, secure: true, sameSite: "lax", path: "/", maxAge: 60*60*24*7 (604800 seconds). The response body echoes { id, name, email, role, regions } but the UI ignores it: it calls refreshUser() (GET /api/auth/me) and router.push("/admin/operations"). lastLoginAt is saved with validateModifiedOnly so a validation error cannot block a sign-in.

SESSION / ME. src/contexts/AuthContext.tsx mounts at the root layout and GETs /api/auth/me with credentials:"include" and cache:"no-store" (required under Next 16). That route decodes the JWT itself (not requireAuth) and ALWAYS answers 200: { success:true, data:null } when there is no token, the token is invalid/expired, the userId is missing, or the user row is missing/inactive; otherwise { success:true, data:{ id, name, email, role, regions, activeRegion, avatar } }. So the UI never sees a 401 here — "logged out" is signalled by data === null, and AuthContext just sets user to null. `regions` and `role` are read from the DB row, never from the token, so a revoked region or role takes effect on the next request instead of in 7 days.

PER-REQUEST AUTH. Every protected API route calls requireAuth(req) / requireRole(req, roles) inline at the top. getUserFromRequest reads ONLY req.cookies.auth_token — there is no Authorization: Bearer path anywhere in this codebase. requireAuth throws AuthError 401 "You aren't authorized to perform this action." when there is no/invalid token or no user row, and 403 "Your account is deactivated." when inactive; requireRole adds a 403 for the wrong role. requireAuth also opens two AsyncLocalStorage contexts (audit actor and region scope) synchronously before its first await — the region scope is what filters every Mongoose query. Three routes bypass requireAuth and verify the token themselves because they must run outside the region scope: /api/auth/me, /api/auth/profile, /api/auth/profile/avatar and /api/auth/profile/password — those return a real 401 { success:false, message:"Unauthorized" }.

PAGE GUARDS. src/proxy.ts (Next 16's middleware) runs on navigations. /admin/authentication/login: if a valid token exists it redirects to /admin/operations. Anything else under /admin: no token -> redirect to the login page; invalid token -> redirect to /admin/authentication/unauthorized. With a valid token it then applies a route-pattern RBAC table (routePermissions) and redirects to /unauthorized when the JWT's `role` is not in the list for that path — e.g. /admin/operations/users [10,45,20,69], /users/:id/edit [10,20], /leads/create [10,15,45,50,60,69,70], /leads/<objectid>/convert [10,45,60,69,70], /clients/<objectid>/projects/create [10,45,60,70], /projects/<objectid>/edit [10,45,60,70], /lead-sources/(upload|uploads) = LEAD_SOURCE_MANAGE_ROLES [10,15,45,69], /lead-sources/* = LEAD_SOURCE_ACCESS_ROLES [10,15,45,69,50,60,65,70]. This guard is page-level only; it does not protect /api, and the JWT's role copy is what it reads.

LOGOUT. AuthContext.logout POSTs /api/auth/logout (no body). The server sets auth_token to "" with httpOnly/secure/sameSite:lax/path:"/" and expires: new Date(0), and deletes active_region. The client clears context, toasts, and after 500ms router.push("/admin/authentication/login").

401/403 IN THE UI. src/lib/auth/handleAuthError.ts is the shared handler used by every list/detail screen: on 401 it toasts (deduped by id "auth-401") and router.replace("/admin/authentication/login"); on 403 it calls the caller's onForbidden(message) and the screen renders <AccessDenied message=... /> instead of the content, and returns true so the caller early-returns. The lead-sources module has its own copy in src/components/admin/operations/lead-sources/api.ts: `send()` throws a typed ApiError(message, status, field, details) for anything that is not res.ok && json.success, and on 401 does window.location.href = "/admin/authentication/login". Field-level errors are conveyed as { success:false, message, field } ("phone", "region", "file", "allottedDay") and forms (LeadForm, ClientForm, CallForm, booking) branch on data.field to attach the message to the right input.

## Region flow
WHAT A REGION IS. src/lib/region.ts defines REGION_CODES = ["IN","US","AE"] with REGIONS metadata (label, phoneCountry) and DEFAULT_REGION = "IN". ALL_REGIONS = "ALL" is deliberately NOT a RegionCode: no record is ever stored with it and no query filter uses it — it only describes what the person is looking at. resolveEffectiveRegion("ALL") returns India, and that single region is what phone parsing and form defaults use.

WHAT THE USER HOLDS. Each User row has regions: RegionCode[]. The login JWT carries a copy ({ userId, role, regions }) but ONLY for src/proxy.ts, which runs at the edge and cannot reach the database; every API route re-reads regions from the user row via getUserFromRequest, on purpose, so revoking a region takes effect immediately instead of after the 7-day token expiry.

HOW A REGION IS CHOSEN AND STORED. The server, not the client, decides. requireAuth calls narrowToActiveRegion(req.cookies.get("active_region")?.value, user.regions) and writes { regions, writeRegion } into the per-request region context; a Mongoose plugin then scopes every query. The cookie is named active_region (ACTIVE_REGION_COOKIE, src/lib/region-scope/activeRegion.ts) and is set httpOnly: true, secure: true, sameSite: "lax", path: "/", maxAge: 604800. It is NOT a header and NOT a JWT claim — the JWT copy of regions is never trusted by API routes. The cookie can only NARROW: narrowToActiveRegion ignores an unreadable, unknown, or no-longer-held value and falls back to "everything the account holds", so forging it can never widen access. No region is sent as a query parameter or request header by any UI fetch; scoping is entirely implicit in the cookie.

WHAT THE UI SHOWS. GET /api/auth/me runs the same narrowToActiveRegion and returns both `regions` (what the account holds) and `activeRegion` (what this session is narrowed to: a code, or "ALL"). AuthContext stores both; RegionContext (src/contexts/RegionContext.tsx) derives serverActive = user.activeRegion ?? (regions.length === 1 ? regions[0] : "ALL"), plus isAll, canSwitch (regions.length > 1) and config = resolveEffectiveRegion(active). RegionSwitcher (in SideBar and MobileTopBar) renders a plain badge when the user holds one region and a dropdown otherwise; it renders nothing until /api/auth/me returns, so a wrong region never flashes.

SWITCHING. RegionContext.setActive(next) POSTs { region: next } to /api/auth/region. That route requireAuths, validates with isSelectableRegion(requested, user.regions) (403 { success:false, message:"You cannot switch to that region. Your account covers: ...", field:"region" } otherwise), then either deletes the cookie for "ALL" or sets active_region to the code. "ALL" clears rather than storing a value so the default is always "whatever the account holds today". It answers with the RESULT, { success, data: { active, regions } }, computed by narrowToActiveRegion — and the UI deliberately trusts json.data.active rather than its own request, then calls window.location.reload() because every list already on screen was fetched under the old scope.

WRITING IN A REGION. For top-level records with no parent to inherit from (a hand-typed Lead, a Client created directly, a lead-source upload), resolveWriteRegion(requested, authUser) decides: if the request names nothing it uses ctx.writeRegion (set when exactly one region is in view), else it demands one ("Pick a region. You are viewing: ..."); a named region must be held by the account (403 "You do not have access to the X region.") AND be in view (400 "You are viewing X. Switch to Y in the header to create a record there."). The UI mirrors this with useWriteRegion/WriteRegionField: the choices are the regions currently in VIEW, not every region held — a dropdown when viewing "ALL" (India preselected), a fixed read-only field when pinned or when the user holds one. LeadForm and ClientForm send `region` only on create (region is immutable after save); the lead-source upload sends it as a FormData field; POST /projects sends no region at all because a project inherits its client's. User creation/editing is different again: resolveGrantedRegions (src/lib/region-scope/regionGrant.ts) lets HR/Admin (canAdministerAllRegions) grant any region while everyone else can only grant regions they hold, keeps regions the target already holds that the granter cannot touch, and refuses an empty result; the Edit User screen only sends `regions` when the set actually changed, because the API 403s a user editing their own regions.

LOGIN/LOGOUT INTERACTION. /api/auth/login deletes active_region before setting the new token, and /api/auth/logout deletes it alongside auth_token, so a region pin never survives a change of user on the same client.

CROSS-REGION READ SCOPE. One extra subtlety: the stats snapshot is keyed per region-set (statsSnapshotKey()), so an admin on "ALL" and a US-only agent never share a cached stats row; and lead-sources/assignees takes an explicit ?regions=US,IN list (users must hold ALL of them, $all) on top of the caller's own region scope.

## What a non-browser client must do differently
- AUTH TRANSPORT — the backend MUST change. getUserFromRequest (src/lib/auth/getUserFromRequest.ts) reads ONLY req.cookies.get('auth_token'); /api/auth/me, /api/auth/profile, /api/auth/profile/avatar and /api/auth/profile/password each read the cookie directly too. There is no Authorization: Bearer path anywhere. React Native's fetch has no cookie jar of its own and no httpOnly storage, so either (a) add a Bearer fallback in getUserFromRequest + those four routes and return the raw JWT in the /api/auth/login response body (it already returns a body, just not the token), or (b) ship a cookie manager (react-native-cookies / a fetch wrapper that stores and replays Set-Cookie). (a) is the smaller, more honest change; it is a one-line read in each of five places plus one extra field in the login response.
- TOKEN STORAGE AND LIFETIME — the 7-day JWT currently lives in an httpOnly cookie the JS never sees. On device it must go into secure storage (Keychain / EncryptedSharedPreferences via react-native-keychain or expo-secure-store), never AsyncStorage. There is no refresh endpoint: after 7 days verifyToken throws TOKEN_EXPIRED and every call 401s, so the app needs an explicit re-login flow. Consider adding a refresh/renew endpoint if a weekly forced login is unacceptable on mobile.
- 'LOGGED OUT' IS NOT A 401 — GET /api/auth/me always answers 200 with data:null for a missing/expired/invalid token. An RN session bootstrap must branch on json.data === null, not on res.status. Only the four token-reading profile routes and requireAuth-protected routes return a real 401.
- REGION TRANSPORT — the backend MUST change. The active region is carried solely by the httpOnly active_region cookie, read in exactly two places: requireAuth (src/lib/auth/requireAuth.ts:63) and /api/auth/me (src/app/api/auth/me/route.ts:92), and written in three (/api/auth/login deletes it, /api/auth/logout deletes it, /api/auth/region sets or deletes it). No route reads a region header or query param. For RN, add an X-Active-Region header (or an equivalent) that those two readers consult with the cookie as fallback — narrowToActiveRegion already ignores anything unknown or not held, and it can only narrow, so accepting it from a header is exactly as safe as accepting it from a cookie. If instead you keep the cookie, POST /api/auth/region becomes useless to RN because the client cannot read the resulting Set-Cookie value reliably.
- REGION STATE ON DEVICE — RegionContext currently reloads the whole page (window.location.reload()) after a switch, which does not exist in RN. The app must instead invalidate every cached list/query (e.g. queryClient.clear() or invalidate all) and refetch, because everything on screen was fetched under the old scope. Persist the chosen region locally and send it on every request, and re-seed it from /api/auth/me's activeRegion on launch so the device can never disagree with the server.
- REGION PIN MUST BE CLEARED ON LOGIN AND LOGOUT — the server does this today by deleting the active_region cookie in both routes. An RN client holding the region in its own storage must replicate that explicitly, or user B inherits user A's pin on a shared device.
- ABSOLUTE URLs — every UI fetch uses a same-origin relative path ('/api/...'). RN needs a configured API base URL (dev/staging/prod, plus 10.0.2.2 vs localhost for the Android emulator) prepended by a single fetch wrapper. The same applies to data coming back: call recordings are stored on the Next server's disk and returned as RELATIVE urls ('/uploads/calls/<file>') by POST /api/admin/operations/calls, and any avatar written before the ImageKit switch may be relative too — RN <Image> cannot resolve those, so prefix them with the API base (or move call recordings to ImageKit so every stored URL is absolute). ImageKit URLs (https://ik.imagekit.io/...) are already absolute and fine.
- FILE UPLOADS — four endpoints take multipart/form-data and read it with Next's req.formData(): POST /api/admin/operations/calls (part 'recording'), POST /api/admin/operations/quotations (part 'file'), POST /api/admin/operations/users and PATCH /api/admin/operations/users/:id (part 'avatarFile' plus repeated 'regions' parts), POST /api/auth/profile/avatar (part 'avatarFile'), and POST /api/admin/operations/lead-sources/uploads (part 'file' plus region/assignedTo/allottedDay/today). In RN you append { uri, name, type } objects to FormData and must NOT set Content-Type manually (the boundary must be generated). Pick files with react-native-document-picker / image-picker; content:// URIs on Android may need copying to a cache file first. The server validates file.type and file.size, so the RN parts must carry a correct MIME type and a real filename, otherwise the 415/413 branches fire. No backend change is needed for these if Bearer auth is added — req.formData() is agnostic to the client.
- REPEATED FORM FIELDS — user create/edit send `regions` as repeated FormData entries (parseRegionsInput also accepts a single JSON-array string). RN FormData supports repeated keys, but if your HTTP layer collapses them, send the JSON-array form instead: formData.append('regions', JSON.stringify(['IN','US'])).
- BINARY DOWNLOADS — the lead-source template (GET /lead-sources/template) and the upload report (GET /lead-sources/uploads/:id/download) are plain <a href download> browser navigations returning .xlsx with Content-Disposition. There is no cookie on an RN Linking.openURL and no download manager, so the app must fetch them with the auth header and hand the bytes to react-native-blob-util / expo-file-system + Sharing, or the backend must issue a short-lived signed download URL. Same for anything else opened by href rather than fetch.
- CLIENT-LOCAL DAY — the lead-sources module sends `today` ('YYYY-MM-DD', the client's local day) on the list query, every status change, the bulk endpoint and the upload. RN must compute this from the device timezone exactly as src/lib/lead-sources/day.ts does, or callbacks and 'today' views land on the wrong day. Callback writes also send callbackAt (ISO) + callbackDay (local day) together.
- ROUTE GUARDS DISAPPEAR — src/proxy.ts enforces page-level RBAC by redirecting on navigation. RN has no equivalent, so its navigator must re-implement the same role tables client-side (routePermissions in src/proxy.ts, LEAD_SOURCE_ACCESS_ROLES / LEAD_SOURCE_MANAGE_ROLES / LEAD_SOURCE_CONVERT_ROLES in src/constants/leadSourceRoles.ts) from the role returned by /api/auth/me — and still handle the API's own 403 by rendering the AccessDenied equivalent, since the API is the real gate. No backend change needed.
- NAVIGATION TARGETS ARE WEB PATHS — GET /api/admin/operations/search returns href strings like '/admin/operations/leads/<id>', and notification rows carry a url used by markOneRead to navigate. RN needs a mapper from those web paths to screen names (or a deep-link config), or the backend should start returning { type, id } alongside href.
- POLLING AND BACKGROUND — NotificationBell polls GET /api/notifications?limit=4 every 30s and the lead-sources list quietly reloads every 60s and on tab focus (document visibility). On device, drive these off AppState instead of document events, stop them in the background to spare battery, and consider FCM push instead of polling (the backend has an in-app Notification collection but no push channel today).
- CORS AND COOKIE ATTRIBUTES — an RN app is not a browser origin, so CORS is not enforced against it, but secure:true cookies will not round-trip over plain http://10.0.2.2:3000 in dev if you keep the cookie approach; another reason to move auth to a header. Only /api/public/leads does origin/x-api-key checks, and the admin app does not call it.
- RESPONSE SHAPE INCONSISTENCIES THE RN CLIENT MUST ABSORB (no backend change required, but a typed client should normalise them): leads/clients return nested data ({ lead, client } / { client, lead, projects }) while projects returns flat data; all three /:id/interactions routes answer { success, interactions } at the TOP LEVEL instead of inside data; meetings paginate with pagination.totalPages while everything else uses pagination.pages; the quotations route reports failures in `error` while everywhere else uses `message`; and src/app/admin/operations/projects/create/page.tsx posts to /api/admin/projects, which does not exist — the RN port must use /api/admin/operations/projects.

## Error handling
Two shared helpers cover everything. (1) src/lib/auth/handleAuthError.ts — used by the dashboard, every list screen (leads, clients, projects, meetings, users, lead-sources, uploads), and every detail screen. It takes (res, json, router, onForbidden) and returns true when it handled the response: on 401 it toasts json.message || "Session expired. Please log in again." with the deduped id "auth-401" and router.replace("/admin/authentication/login"); on 403 it calls onForbidden(json.message || "You aren't authorized to perform this action.") and the screen swaps its body for <AccessDenied message=... />. Callers early-return on true. (2) src/components/admin/operations/lead-sources/api.ts `send()` — the whole lead-sources module goes through it. It throws a typed ApiError { message, status, field, details } whenever !res.ok || !json.success, and on 401 additionally does window.location.href = login. Callers catch and toast error.message; UploadForm reads error.details.missing/found to list the bad sheet columns.

Envelope: success is { success: true, data, pagination? } (with the documented exceptions: `interactions` at top level on the three timeline routes, `counts`/`progress` on the lead-sources list, `unseen`/`unread`/`total`/`nextCursor` on notifications). Failure is { success: false, message } with the real status code — 400 validation, 401 AuthError, 403 AuthError/role/RegionChoiceError, 404 not found, 409 conflict (duplicate phone, meeting already closed, uneditable interaction type, booking slot taken), 413 file too large, 415 wrong file type, 500 per-handler message. Field-level errors add `field`: "phone" (validatePhone / findLeadPhoneConflict), "region" (resolveWriteRegion, resolveGrantedRegions, /api/auth/region), "file" and "allottedDay" (lead-source uploads). Forms branch on data.field before the generic throw — LeadForm/ClientForm/CallForm call phone.setError(data.message), the booking screen maps field -> input. The quotations route is the odd one out: it returns `error` instead of `message`, and QuotationForm reads data.error.

Patterns an RN client should keep: optimistic updates with rollback on notifications (mark-read/mark-all-read update state first, then refetch the feed if the PATCH fails) and on lead-source row changes (the mutation answers with the updated row, which is swapped in place before a full reload); stale-response guards via a monotonic request-id ref in SearchBar, ActivityLogList and LeadSourcesClient (responses whose id is not the newest are dropped); silent failure for the ambient panels (StatsPanel, OverallStatsPanel, UpcomingMeetingsPanel just .catch(() => {}) and render placeholders); and toast.promise around the interaction modals (note/call/quotation/meeting) so one promise drives loading/success/error text.

# Lead sources module (cold calling)

## What it does
LEAD SOURCES is a bulk cold-calling module, deliberately kept separate from the Lead model. A manager uploads an Excel/CSV list; each accepted row becomes one `LeadSource` document (one number to call), optionally pre-assigned to a person (`assignedTo`) and a calendar day (`allottedDay`, plain "YYYY-MM-DD" text, no timezone). An agent opens the list, sees "Today" (due callbacks pinned at the top), calls the number, picks the result of the call from a status menu, types a short note, and optionally schedules a callback. Good conversations are converted into a real `Lead` in one Mongo transaction; the rest close as Not Interested.

Key source files (all under the ref clone root ):
- docs: `docs/lead-sources.md` (306 lines, the authoritative spec — read it first for the RN port)
- constants: `src/constants/leadSourceStatus.ts`, `src/constants/leadSourceRoles.ts`
- wire types: `src/types/leadSource.ts` (LeadSourceRow, LeadSourceDetail, LeadSourceListResponse, LeadSourceCounts, LeadSourceUploadSummary/Report, LeadSourceAssignee) — these are the exact JSON shapes an RN client consumes, so they can be copied verbatim
- sheet config: `src/config/leadSourceSheet.ts` (columns, headers, `maxRows: 5000`, `maxFileMb: 5`, `maxCellLength: 500`, `keepUnknownColumns: true`)
- models: `src/models/LeadSource.ts`, `src/models/LeadSourceUpload.ts`
- server logic: `src/lib/lead-sources/` (mutations 509 lines, upload 377, listQuery 240, convert 207, access/day/activity/serialize/detail/assignee/audit/http/countries/uploadView + `sheet/` subfolder)
- API: `src/app/api/admin/operations/lead-sources/**` (13 handlers)
- pages: `src/app/admin/operations/lead-sources/**` (5 screens)
- components: `src/components/admin/operations/lead-sources/**` (22 files)

Three concepts a mobile port must preserve exactly:
1. The day is TEXT, not a timestamp. The client computes its own local "today" (`todayString()` in `src/lib/lead-sources/day.ts`) and sends it as a `today` field on every list request and every status/day/bulk mutation. The server only sanity-checks it is within ±1 day of UTC (`resolveClientToday`).
2. Callbacks are a real timestamp (`callbackAt`) PLUS the local day they fall on (`callbackDay`), both sent by the client because only the client knows the timezone (`parseCallback` in `src/lib/lead-sources/activity.ts`).
3. Every write answers with the updated `LeadSourceRow`, so the UI swaps the row in place and then quietly reloads 900 ms later.

Not built yet (section 11 of the doc): real dialing (`src/components/admin/operations/lead-sources/dialer.ts` is a stub that only shows/copies the number), callback reminders outside the open page (needs a scheduled job), a Do-Not-Call status, editing name/phone/email, and splitting a list between several people.

## Status model
Defined in `src/constants/leadSourceStatus.ts`.

LEAD_SOURCE_STATUS (the result of the latest call):
- 10 NEW — "New", not called yet, open
- 20 NOT_REACHED — "Not Reached" (no answer, busy, switched off, voicemail, invalid number), open
- 30 CALL_BACK — "Call Back" (they asked us to call later), open
- 40 INTERESTED — "Interested", open
- 50 NOT_INTERESTED — "Not Interested" (incl. working with someone else, no need, do-not-call, wrong number), CLOSED
- 70 CONVERTED — "Converted", CLOSED, set only by the convert route
- 60 is RETIRED (was "Wrong Number", folded into 50). Never reuse 60 — old DB rows may still hold it, and `LEAD_SOURCE_STATUS_META[60]` is undefined, so any RN status renderer must fall back ("Unknown"/grey) exactly like `StatusPill.tsx` does.

Transitions: there is NO pipeline and no ordering. Any status may follow any other, with two hard rules:
- CONVERTED (70) is terminal and only `POST /:id/convert` sets it. `assertNotConverted()` in `src/lib/lead-sources/mutations.ts` returns 409 "This lead source is already a lead. Open the lead to continue." for status/callback changes on a converted source. `LEAD_SOURCE_PICKABLE_STATUSES` excludes 70, so the picker never offers it.
- A status change is saved with an optimistic guard `{ status: source.status }`; if it changed in between the request gets 409 "This lead source changed while you were saving. Reload it and try again."

Side effects of a status change (`changeStatus`):
- `allottedDay` is set to the client's `today` (the day it was actually worked) — EXCEPT for CALL_BACK, where it becomes the callback's day.
- CALL_BACK requires `callbackAt` + `callbackDay`; every other status sets `callbackAt: null`.
- Writes `lastNote`/`lastNoteAt` when a note was typed, sets `lastActivityAt`, and pushes an activity entry.

Callback-only change (`setCallback`, `PATCH /:id/callback`): sets/changes/clears the time without picking a status. A NEW source or a CLOSED one that gets a callback is reopened to CALL_BACK (30); any other open status is kept. `{ callbackAt: null }` clears it. Validation: must be in the future (10 min slack), at most 366 days ahead, `callbackDay` must match `callbackAt`'s UTC day within one day.

Manager setting the day (bulk `day` action) always clears `callbackAt`.

Callback urgency states (client-side, `callback.ts` + `useNow.ts`): "later" (violet chip), "soon" = within 15 min (amber chip, slow ring animation), "due" = time passed (red chip, pulsing + ringing clock, red left edge on the row, pinned to section 0 of Today).

Closed statuses (50, 70) drop out of Today / Upcoming / No day and appear only in Closed and All.

LEAD_SOURCE_ACTIVITY (timeline entry codes on the embedded `activity` array): 10 UPLOADED, 20 NOTE, 30 STATUS, 40 CALLBACK, 50 ASSIGNED, 60 DAY, 70 CONVERTED.

UPLOAD_ROW_RESULT: 10 IMPORTED, 20 WARNED ("Imported with warnings"), 30 SKIPPED. UPLOAD_STATUS: 10 PROCESSING, 20 DONE, 30 FAILED.

## Roles and access
Defined in `src/constants/leadSourceRoles.ts`; the API routes, the Next.js page guard (`src/proxy.ts` lines 30-31), the sidebar (`SideBar.tsx` line 15) and the MobileNav (labelled "Calls", `MobileNav.tsx` line 30-35) all read it.

- MANAGE = [10 Admin, 15 Operations Manager, 45 Senior Blockchain Dev, 69 US Leads Manager]. Sees EVERY source in their regions. Can upload sheets, assign, set the day, delete, and see upload reports. Also everything WORK can do.
- WORK = [50 Digital Marketer, 60 BDE, 65 US Sales Agent, 70 Accountant]. Sees ONLY sources where `assignedTo == self`. Can call, set status, add notes, set callbacks.
- CONVERT = [10, 15, 45, 50, 60, 69, 70] — same list as "create a lead" in `POST /api/admin/operations/leads`. Note 65 (US Sales Agent) is deliberately NOT in CONVERT: they mark Interested and a manager converts.
- LEAD_SOURCE_ACCESS_ROLES = MANAGE + WORK — anyone who can open the module at all.
- Helpers: `canUseLeadSources(role)`, `canManageLeadSources(role)`, `canConvertLeadSources(role)` — all pure functions, directly portable to RN.

Enforcement layers (all server-side, never trust the client):
1. `requireRole(req, LEAD_SOURCE_ACCESS_ROLES | LEAD_SOURCE_MANAGE_ROLES | LEAD_SOURCE_CONVERT_ROLES)` at the top of each route.
2. `accessFilter(user)` in `src/lib/lead-sources/access.ts` — `{}` for managers, `{ assignedTo: ObjectId(user.id) }` for everyone else. Added to every read AND every write.
3. `regionScopePlugin` on the model adds the region condition to every query automatically. Region ("IN" | "US" | "AE", `src/lib/region.ts`) applies on top of every role list — a US Leads Manager only ever sees US sources. A user may hold several regions; `ALL_REGIONS = "ALL"` is a view-only pseudo-region that never reaches a query.
4. `softDeletePlugin` filters `deletedAt`.

A source in another region or assigned to someone else returns the same 404 "Lead source not found." as one that does not exist — the response never confirms existence.

Assignee validation (`resolveAssignee` in `src/lib/lead-sources/assignee.ts`): the target must be `isActive`, have a role in LEAD_SOURCE_ACCESS_ROLES, and hold EVERY region of the sources being assigned (`regions: { $all: regions }`), otherwise 400 with a message naming the regions.

Client-side gating in the web UI (to mirror in RN): `isManager` hides/shows the "Upload sheet" button, the manager filter bar (person / one day / upload), the assignee avatar column, and the Assign/Day/Delete buttons in the bulk bar and on the detail page; `canConvert && !converted` shows "Convert to lead".

## Flows

### Cold call -> status change -> note (the core loop, 2 taps)
1. Agent opens the list; the server returns the Today view already sorted: section 0 due callbacks (oldest first), section 1 today's (timed callbacks first, then New before already-tried), section 2 earlier days (most recent first). 2. Agent taps the green CallButton -> `startCall()` in `src/components/admin/operations/lead-sources/dialer.ts` -> today this only shows a toast with the formatted number and a 'Copy number' action; it is the single seam where a real dialer plugs in. 3. Agent taps the status badge -> Popover (bottom sheet under 640px) with a 2-column radio grid of `LEAD_SOURCE_PICKABLE_STATUSES` (New / Not Reached / Call Back / Interested / Not Interested, the current one marked 'now'), an optional 2-row note textarea (max 2000 chars, Enter saves, Shift+Enter newlines), and, if Call Back is picked, the CallbackPicker. 4. Save -> `PATCH /:id/status` with `{ status, note?, today, callbackAt?, callbackDay? }`. 5. Server (`changeStatus` in mutations.ts): validates the status is pickable (400 'Pick a valid status.'), rejects converted sources (409), resolves the client's today, sets `allottedDay = today` (or the callback's day), sets `callbackAt` (null unless Call Back), writes `lastNote`/`lastNoteAt`/`lastActivityAt`, pushes a STATUS (30) activity entry with `{from, to, text, callbackAt?}`, and saves through `findOneAndUpdate` guarded by `{_id, ...accessFilter(user), status: <previous>}` -> 409 on a concurrent change. Then logs the field-level diff to the activity log. 6. Response is the updated `LeadSourceRow`; the UI swaps it in immediately, toasts, and quietly reloads 900 ms later so the row re-sorts and the tab counts follow.

### Add a note without changing the status
1. On the detail page, type into NoteBox (Ctrl+Enter or the 'Add note' button). 2. `POST /:id/notes` with `{ text }`. 3. Server: `parseNote` trims, rejects non-strings ('The note must be text.') and >2000 chars; empty text is 400 'Write a note first.'. 4. Sets `lastNote`/`lastNoteAt`/`lastActivityAt`, pushes a NOTE (20) activity entry. The guard is `{}` (visibility only) because a note does not depend on the status — so a note still saves on a converted source. 5. Returns 201 with the updated row; the detail page merges it and reloads for the new timeline entry.

### Callback scheduling (the feature a phone does best)
1. From the status menu (picking Call Back) or from the standalone clock chip / 'Set callback' button. 2. CallbackPicker offers presets from `CALLBACK_PRESETS` in `callback.ts`: 15 min, 30 min, 1 hour, 2 hours, 4 hours, Tomorrow 10 AM, plus an exact `datetime-local` input. 3. The client computes the moment and sends BOTH `callbackAt` (ISO) and `callbackDay` (`toDayString(at)`, the local day) — the server cannot derive the local day itself. 4. `PATCH /:id/callback` with `{ callbackAt, callbackDay, note? }`, or `{ callbackAt: null }` to clear. 5. Server (`setCallback`): rejects converted (409); validates the time is not more than 10 minutes in the past, not more than 366 days ahead, and that `callbackDay` is a real day matching `callbackAt`'s UTC day within 24h; reopens NEW or CLOSED sources to CALL_BACK (30) and keeps any other open status; sets `allottedDay` to the callback's day; pushes a CALLBACK (40) activity entry. 6. On screen: `useNow(15_000)` re-renders the chips every 15 seconds so 'in 16 min' becomes 'soon' (amber, slow ring) then 'due' (red, ringing + pulsing, red row edge) without a server round-trip; the 60s quiet reload then moves the row into section 0. 7. Nothing notifies the agent when the app is closed — this is the biggest named gap (doc section 11.2: needs a scheduled job).

### Convert to lead
1. 'Convert to lead' on the detail page (CONVERT roles, hidden once converted) -> confirm dialog. 2. `POST /:id/convert`. 3. Server (`src/lib/lead-sources/convert.ts`): loads the visible source; 409 if already CONVERTED or `convertedLeadId` set; `findLeadPhoneConflict(phone, region.phoneCountry)` -> 409 with `field: 'phone'` if the number already exists as a Lead. 4. Inside ONE Mongo transaction: creates the Lead (name, email, phone, `source = 'Cold Call'`, region, `assignedTo` = the source's assignee or the actor, `createdBy`, `lastInteractionAt/Id` pointing at the note), creates an Interaction of type NOTE_ADDED titled 'Converted from a lead source' whose body is built by `conversionNote()` (who converted it, the file name + row + upload date, every remaining sheet column as 'Label: value' including unknown columns, then the last 20 call notes as 'YYYY-MM-DD, Name [Status]: text'), and updates the source to CONVERTED + `convertedLeadId` + `convertedAt` + `callbackAt: null` + a CONVERTED (70) activity entry, guarded by `status != CONVERTED`. 5. The unique index on `Lead.phone` is the race-stopper: a duplicate-key (11000) becomes 409 DUPLICATE_LEAD_MESSAGE and nothing is saved. 6. After commit: the activity-log diff is written (the in-transaction updateOne bypasses the audit plugin), and `emitNotification({ type: EVENT_CODE.LEAD_CREATED, ... })` fires — the same notification as a hand-created lead. 7. Returns 201 `{ leadId }`; the UI navigates to `/admin/operations/leads/:leadId`.

### Sheet upload -> parse -> rows
1. Manager picks an .xlsx/.csv, optionally an assignee and a day, and posts multipart to `POST /uploads`. 2. Route validates: file present, region resolvable (`resolveWriteRegion`), assignee valid for the region, day is a real day, not in the past, within 366 days. 3. `processUpload` (`src/lib/lead-sources/upload.ts`): size check (5 MB, 413), empty check, `readSheetFile` (read-excel-file/universal for xlsx — NOT /node, which breaks `next build`; a hand-written CSV reader in `sheet/csv.ts` so leading zeros survive). 4. `findHeaderRow` scans the first 10 rows for the first row holding every required column; headers are normalised (lowercase, runs of spaces/dots/dashes/slashes/underscores -> one underscore) and matched against each column's `key` or `headers` list. FILE-LEVEL refusals (nothing is saved, 400): a required column missing (with `details.missing` + `details.found` so the UI can show both), two headers meaning the same column, unknown headers when `keepUnknownColumns: false`, an unreadable file, no data rows, more than 5,000 rows, or a report that would exceed ~10 MB of text (413 'Split it into smaller files.'). 5. `checkRows` validates every row. ROW-LEVEL skips: an empty required cell, a phone that is not one valid number, a phone repeated earlier in the same file. ROW-LEVEL warnings (still imported): an extension on the phone, two numbers in one cell (first valid one used), an invalid email (kept in sheet data, not used as the email), an unparseable date (kept as text), a cell over 500 chars (cut). Phones without a '+' are parsed with the row's own `country` column (names mapped in `src/lib/lead-sources/countries.ts`), falling back to the upload region's country; dates read `03/04/2021` as MDY for US uploads and DMY otherwise, and also handle Excel serial numbers like 43845. 6. `skipKnownPhones` then skips rows whose phone is already a lead source in this region (message names the existing status) or already a Lead anywhere, deleted or not (checked through the raw driver across regions, because that is the reach of the unique index — the message never names the lead). 7. Creates the LeadSourceUpload (status PROCESSING), inserts the good rows with `insertMany` in chunks of 1,000 (each with an UPLOADED (10) activity entry naming the file and row), then updates the upload with the full report (columns, missingColumns, fileNotes, every row's values + result + messages + sourceId) and status DONE. 8. On any failure the sources are deleted and the upload is marked FAILED, so sources never exist without a report. 9. Returns 201 `{ uploadId, counts }`; the UI navigates to the report.

### Bulk actions
1. Tick rows (or use the header 'select all on this page' checkbox, which supports an indeterminate state) -> BulkBar appears -> a dialog per action. 2. All four actions post to the SAME endpoint `POST /bulk` with `{ ids, action, ...values, today }`, max 200 ids. 3. `status` — anyone, on sources they can see; Call Back is explicitly refused in bulk ('Set Call Back one source at a time, so each one gets its own time.'); sets `allottedDay = today`, clears callbacks, skips converted rows. 4. `assign` — managers only; `resolveAssignee` enforces active + lead-source role + holds every region in the selection; records the previous assignee's NAME in the timeline. 5. `day` — managers only; also clears `callbackAt` and says so in the timeline entry. 6. `delete` — managers only; SOFT delete (`deletedAt` + `deletedBy`); converted Leads are untouched and the upload reports still show the rows. 7. Implementation detail that matters for parity: the server reads the visible docs first, then issues one `updateMany` PER GROUP of identical old value, repeating the read's conditions, so a row changed in between is left alone rather than overwritten; `updateMany` bypasses the audit plugin so audit rows are written by hand through `src/lib/lead-sources/audit.ts`. 8. Returns `{ updated, unchanged, skipped }`, which the UI renders as '12 lead sources assigned. 3 already set. 1 skipped.'

### Reports and counting
There is no separate reports screen; reporting is folded into the list and the upload report. (a) The list endpoint returns `counts` for all five tabs plus `callbacksDue` in one response, computed by seven parallel `countDocuments` calls over `countFilters()`. (b) `progress: { total, worked }` counts sources allotted to today and how many are no longer New — rendered as the Today progress bar. (c) The upload report gives per-file read/imported/warned/skipped tiles and the full row grid. (d) Downloadable .xlsx reports (`buildReportWorkbook` in `sheet/workbook.ts`) with coloured rows per result and a Summary sheet; every value is written as a TEXT cell so a value starting with '=' can never execute as a formula.

## Endpoints
- GET /api/admin/operations/lead-sources — one page of one view plus every tab count and today's progress. Query: view (today|upcoming|unscheduled|closed|all), today, day, status, assignee (userId|'me'|'none'), upload, search, page, limit (default 50, max 100). Roles: ACCESS. Returns { success, data: LeadSourceRow[], pagination, counts: {today,upcoming,unscheduled,closed,all,callbacksDue}, progress: {total,worked} }. Rows in the 'today' view carry `section` 0/1/2. Search matches name, company, email, lastNote, the sheet columns flagged `searchable` (domain_name, domain_company_name, city, name, company, email, phone) and the phone by its digits when >= 4 digits.
- GET /api/admin/operations/lead-sources/:id — one source with `data` (every sheet cell), `importNotes`, `activity` (newest first), `upload` {_id,fileName,createdAt} and `convertedLead` {_id,name}. Roles: ACCESS. 404 for anything outside the caller's region/assignment.
- PATCH /api/admin/operations/lead-sources/:id/status — body { status, note?, today, callbackAt?, callbackDay? }. Roles: ACCESS. Returns the updated LeadSourceRow. 400 bad status/note/callback, 404 not visible, 409 converted or changed-while-saving.
- POST /api/admin/operations/lead-sources/:id/notes — body { text }. Roles: ACCESS. 201 with the updated LeadSourceRow.
- PATCH /api/admin/operations/lead-sources/:id/callback — body { callbackAt, callbackDay, note? } to set, or { callbackAt: null } to clear. Roles: ACCESS. Returns the updated LeadSourceRow.
- POST /api/admin/operations/lead-sources/:id/convert — no body. Roles: CONVERT. 201 { leadId }. 409 on already-converted or a duplicate lead phone.
- POST /api/admin/operations/lead-sources/bulk — body { ids (max 200), action: 'status'|'assign'|'day'|'delete', today, + status/note | assignedTo | day }. Roles: ACCESS for 'status', MANAGE for the other three. Returns { updated, unchanged, skipped }. Also used by the detail page with a single id.
- GET /api/admin/operations/lead-sources/assignees?regions=US,IN — people who can take sources in ALL the given regions (active, lead-source role, region-scoped to the caller too). Empty `regions` returns everyone with a lead-source role in the caller's regions (used by the person filter). Roles: MANAGE. Max 300, sorted by name. 400 'Unknown region: X'.
- GET /api/admin/operations/lead-sources/template — a blank .xlsx built from leadSourceSheet.ts with a second sheet explaining each column. Roles: MANAGE. Binary response, Content-Disposition attachment, no-store.
- GET /api/admin/operations/lead-sources/uploads?page=&limit= — upload history, newest first, without the rows/columns payload. Roles: MANAGE. limit default 20, max 50.
- POST /api/admin/operations/lead-sources/uploads — multipart/form-data: file (.xlsx|.csv), region?, assignedTo?, allottedDay?, today. Roles: MANAGE. 201 { uploadId, counts: {read,imported,warned,skipped} }. Error bodies may carry `field` and `details: { missing, found }`.
- GET /api/admin/operations/lead-sources/uploads/:id — one upload with its full report: columns, missingColumns, fileNotes, and every row { n, values[], result, messages[], sourceId? }. Roles: MANAGE.
- GET /api/admin/operations/lead-sources/uploads/:id/download?only=imported|warned|skipped — the report as .xlsx with coloured rows and a Summary sheet; `only` narrows it so skipped rows can be fixed and re-uploaded. Roles: MANAGE.

## What a phone does better
- REAL DIALING — the single biggest win, and the code is already shaped for it. `startCall()` in dialer.ts is the only place any call button goes through; swapping its body for `Linking.openURL('tel:' + phone)` on Android turns the whole module from 'copy this number and type it into your phone' into one tap. Everything else (row layout, detail page, statuses) already assumes a call just happened.
- AUTOMATIC CALL LOGGING — Android can report call state and duration (READ_PHONE_STATE / CallLog, or a ConnectionService). Returning to the app after a call can open the status sheet pre-filled: outcome suggested from duration (0 s / missed -> Not Reached; >30 s -> ask the result), with the real call duration and timestamp attached to the note. The web version can never know whether the call happened at all.
- POST-CALL AUTO-PROMPT — detect the call ending and immediately present the status sheet as a full-screen native sheet. This removes the find-the-row-again step, which is the slowest part of the web loop on a phone.
- REAL CALLBACK REMINDERS — the doc explicitly lists this as not built (section 11.2: 'A due callback shows only while the list is open... that needs a scheduled job'). On Android a local notification scheduled at `callbackAt` when the callback is saved solves it with no server work at all: no cron job, no push infrastructure, works offline, and fires even when the app is closed. Cancel/reschedule the local notification whenever `callbackAt` changes or the status moves off Call Back. This is the clearest case where the phone version is strictly better than the web one.
- ONE-HANDED USE — the action targets (status badge, clock chip, call button) are currently small chips in the top-right of each row. On a phone they should be a swipe gesture (swipe right = call, swipe left = set status) or a bottom-anchored action sheet, keeping everything in the thumb arc. The BulkBar and Popover already anchor to the bottom, so the design direction is established.
- OFFLINE LIST + QUEUED WRITES — the Today view is a small, bounded, personal list (an agent's day: tens of rows, not thousands). Cache it in SQLite/MMKV on login, let the agent work a basement or a parking lot, and queue status/note/callback mutations. The API is already a good fit: every mutation is a small idempotent-ish JSON patch on one id, and the server's optimistic guard (`{status: <previous>}` -> 409) gives a precise, already-implemented conflict signal to replay or surface. Keep bulk and convert online-only.
- NATIVE CONTACT ACTIONS — WhatsApp is already deep-linked on the detail page; on Android add 'Send SMS', 'Save to contacts', and a share sheet for the number. Also the OS call-screen caller ID becomes possible (showing the company name on an incoming callback) via a CallScreeningService.
- VOICE NOTES — the note field is free text up to 2000 chars and is the main record of what happened on a call. On a phone, speech-to-text (or recording + transcription) is dramatically faster than typing after every call, and these notes are what get copied into the Lead on convert.
- LOCATION / ROUTE CONTEXT — the sheet already carries address, city, state, zip and country. A field agent could sort or map today's list by distance, or open directions, which a desktop user never needs.
- QUICK TRIAGE WIDGET / NOTIFICATION — 'N callbacks due' as an Android notification or home-screen widget replaces the in-page red banner that only exists while the browser tab is open.
- PULL-TO-REFRESH replaces the 60-second quiet polling loop (and its visibilitychange/menu-open suppression logic), saving battery and data while keeping the same freshness guarantee.

## Risks
- TIMEZONE AND THE 'today' CONTRACT — the client computes its own local day and sends it on every list read and every status/day/bulk write; the server only checks it is within ±1 day of UTC (`resolveClientToday`). An RN client must send `today` on EVERY one of those calls or sources silently land on the wrong day. Worse on mobile than web: a phone changes timezone (travel), can run with automatic time off, and can sit backgrounded past midnight with a stale `todayString()` captured in state. Recompute `today` at request time, and re-evaluate on AppState 'active' and on a date change.
- CALLBACK DAY/TIME PAIR — `callbackAt` (ISO) and `callbackDay` (local YYYY-MM-DD) must agree within 24 hours or the server returns 400 'The callback day does not match the callback time.' Any RN date-picker that returns UTC, or a preset computed from a stale clock, will trip this. Also note `parseCallback` rejects times more than 10 minutes in the past — a user who picks a preset, gets interrupted, and saves 20 minutes later gets a 400.
- NO PUSH / NO SERVER-SIDE REMINDER EXISTS — there is no job, no cron, no push token anywhere in the module. If the mobile version promises callback reminders, that is new infrastructure (local notifications are the cheap path; cross-device reminders are not). Local notifications must be kept in sync with every status/callback/day change, including changes made by a manager on the web, which the phone will not learn about until its next fetch.
- AUTH IS COOKIE-BASED — `getUserFromRequest` reads `req.cookies.get('auth_token')` only (no Authorization: Bearer path in this repo). An RN client cannot rely on a browser cookie jar; the backend needs a Bearer branch (the Express port plan already calls for it) and the app needs secure token storage plus a refresh story. Today a 401 just does `window.location.href = '/admin/authentication/login'` in api.ts — that whole path must be rewritten.
- ANDROID CALL PERMISSIONS AND POLICY — CALL_PHONE, READ_PHONE_STATE and especially READ_CALL_LOG / CallLog access are restricted Play Store permissions requiring a declared, approved use case; call recording is effectively blocked on modern Android and is legally fraught. If automatic call logging is in scope, budget for a Play Console permissions review, and design a graceful degraded mode (manual status entry) for when permission is refused.
- DO-NOT-CALL / TCPA EXPOSURE — the doc flags it (section 11.3): US cold calling has legal do-not-call rules and today a DNC request is only recorded as Not Interested with a free-text note. A phone app that dials with one tap makes accidental re-dialing of a DNC number easier and more likely. Add a distinct closed status and a visible block before shipping a one-tap dialer, not after.
- PHONE PARSING DEPENDS ON libphonenumber-js AND THE REGION — numbers are stored E.164 but parsed with the row's `country` column or the region's default; the doc warns '4155550123 is a US number, but with India as the default it reads as an Indian number.' RN must bundle the same library and the same RegionContext `phoneCountry`, or display and dialing will diverge from the server.
- RETIRED STATUS CODE 60 — `LEAD_SOURCE_STATUS_META[60]` does not exist but old DB rows can still hold it. Any RN code doing `META[status].label` without the `?? 'Unknown'` fallback that StatusPill.tsx has will crash on those rows.
- OPTIMISTIC-GUARD 409s ARE NORMAL, NOT EXCEPTIONAL — `updateOne` guards on the previous status, and bulk writes re-check every condition. On a flaky mobile connection with retries, 409 'This lead source changed while you were saving' will be common. The RN client needs a defined behaviour (refetch the row and re-present, never silently discard the user's note text) — losing a typed call note is the worst possible failure here.
- THE DETAIL ROUTE RETURNS THE WHOLE ACTIVITY ARRAY — `activity` is an embedded, unbounded array on the document with no pagination. A long-worked source makes the detail payload grow forever on a metered connection.
- UPLOAD REPORTS ARE HUGE AND UNPAGINATED — `GET /uploads/:id` returns EVERY row of the file in one response (up to 5,000 rows, up to ~10 MB of text by the server's own guard). Fetching that on mobile data will stall or OOM. If the report screen is ported, the API needs row pagination first — that is a server change, not a client one.
- THE SPREADSHEET GRID DOES NOT TRANSLATE — ReportGrid's frozen panes and arbitrary column count assume a wide pointer-driven screen. Re-designing it as cards is a real design task, not a mechanical port.
- FILE UPLOAD ON ANDROID — multipart with a 5 MB file via the Storage Access Framework, surviving backgrounding and doze, plus the .xlsx/.csv template DOWNLOAD (two binary endpoints with Content-Disposition) all need native file handling and a share/open-with flow. Consider leaving the upload flow on the web for v1.
- REGION SCOPE IS INVISIBLE TO THE CLIENT — `regionScopePlugin` silently filters every query, and `resolveWriteRegion` decides the write region from the user's regions. A multi-region user's RN app must carry the same region context or will show confusingly empty lists with no error.
- ROLE LISTS ARE HARD-CODED NUMBERS IN A SHARED FILE — leadSourceRoles.ts is imported by the API, the page guard, the sidebar AND the buttons. An RN app duplicating those arrays will drift the moment someone edits one list (e.g. adding role 65 to CONVERT, which the doc explicitly anticipates). Serve the capability flags from the API, or share one constants package across web/RN.
- BACKEND IS MID-MIGRATION — the working directory's CLAUDE.md describes porting this same Next.js API to Express, and this module (lead-sources) is NOT in that session plan's module list at all. The RN app will be built against an API that is itself being rewritten; pin which backend the app targets and make sure lead-sources is added to the Express port plan, or the app will be built against routes nobody is porting.
